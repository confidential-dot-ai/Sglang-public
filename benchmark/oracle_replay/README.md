### Oracle-mode dataset replay

Replays a real multi-turn agent trajectory through oracle mode
(`SamplingParams.forced_token_ids`, see `feat/oracle-decode-mode`) instead of
a synthetic one-shot benchmark, so throughput/KV-cache/prefix-cache numbers
reflect real agentic traffic shape rather than GPQA/GSM8K-style single-turn Q&A.

Source: [`Wejh/ninja-agent-traces`](https://hf.co/datasets/Wejh/ninja-agent-traces)
(HF dataset, `payloads` config) -- real multi-turn SWE-agent trajectories
generated by the open-weight `Qwen/Qwen3.6-27B-FP8`. Unlike most public agent
trace datasets, reasoning is kept inline in each turn's content (up to a
literal `</think>` marker) rather than stripped down to just the final answer
or tool call -- verified by hand on a sample trajectory before building this.
No explicit license tag on the dataset as of writing; check before using
outputs beyond internal benchmarking.

Each turn is retokenized with the *target* model's own tokenizer (not the
source Qwen tokenizer) -- the goal is a realistic-length, realistic-shaped
token sequence in the target model's vocab, not literal cross-tokenizer IDs.

#### 1. Get payload shards

```bash
curl -sL "https://huggingface.co/datasets/Wejh/ninja-agent-traces/resolve/refs%2Fconvert%2Fparquet/payloads/train/0000.parquet" -o payloads_0000.parquet
# ... repeat for however many of the 14 shards you want (~3.4GB total)
```

#### 2. Build the replay JSONL

```bash
python3 build_trace.py \
  --payloads-parquet "payloads_*.parquet" \
  --tokenizer MiniMaxAI/MiniMax-M3 \
  --num-rollouts 50 \
  --output-dir ./traces
```

Or `--rollout-id <id>` (repeatable) to target specific rollouts. One JSONL
file per rollout is written, one line per turn:
`{"messages": [...], "sampling_params": {"forced_token_ids": [...], "max_new_tokens": N}}`.

#### 2b. Build an explicitly modeled long-conversation corpus

`build_long_conversations.py` creates a deterministic capacity-test corpus
with a requested live-turn count, served-token band, and output share. It
stitches real continuation deltas, adds a unique stable project archive per
conversation, and resizes forced completions proportionally:

```bash
python3 build_long_conversations.py \
  --source /path/to/oracle-realmix-800-r132-m3.json \
  --output /path/to/oracle-realmix-800-r132-m3-modeled-long25-38k-v3.json \
  --tokenizer /data/MiniMax-M3-NVFP4 \
  --target-turns 25 \
  --target-served-tokens 38000 \
  --output-share 0.0075
```

The output metadata labels this transform `modeled-mix`; it is synthetic and
must not be reported as an unmodified production trace. Content-token geometry
in the metadata is an estimate. The replay driver's usage counters remain the
authority for actual served tokens, cache hit, and output share.

For a bounded workload sampled from the public UW SyFI TraceLab token geometry,
use `build_coding_agent_workload.py`. It generates Codex, Claude, mixed, and
saturated Codex variants from real contiguous session windows while replacing
sanitized prompt content with deterministic exact-length text:

```bash
python3 build_coding_agent_workload.py \
  --trace /path/to/syfi_coding_trace.jsonl.gz \
  --oracle-source /path/to/oracle-realmix-800-r132-m3.json \
  --tokenizer /path/to/MiniMax-M3-tokenizer \
  --output-dir /path/to/datasets \
  --max-steps 25 \
  --max-context-tokens 250000
```

These files are labeled `tracelab-modeled-v1`, not verbatim TraceLab content.
The 25-step bound keeps them practical for the current JSON replay path. Use
`concurrent_replay.py --use-dataset-gaps` for empirical timing; omit it for
saturated capacity tests. The driver honors per-turn `reset_history` markers
for sampled compaction and context discontinuities.

The archive is appended to the first existing system/developer instruction.
This matters for chat templates that render only the first instruction message:
inserting a separate system message could otherwise hide the source trace's
original prompt and invalidate the requested depth. Appending also preserves
the original instruction as a shareable radix prefix across conversations.

#### 3. Replay against a live server

```bash
python3 replay.py --base-url http://127.0.0.1:30000 --model <served-model-name> traces/<rollout_id>.jsonl
```

Turns within one rollout **must** run sequentially (each forced completion
becomes real prefix-cache content for the next turn) -- different rollouts
are independent and safe to run concurrently against the same server.

#### 3b. Or: run through sglang's real bench_serving harness

`replay.py` above is a minimal one-rollout-at-a-time runner. For proper
concurrency across many rollouts plus real TTFT/ITL/throughput metrics, use
`--dataset-name oracle-trace` (added alongside oracle mode), which plugs into
the same multi-turn machinery `agentic-trace`/`mooncake` already use:

```bash
python3 build_trace.py \
  --payloads-parquet "payloads_*.parquet" \
  --tokenizer MiniMaxAI/MiniMax-M3 \
  --num-rollouts 50 \
  --combined-output ./combined.json

python3 -m sglang.benchmark.serving \
  --backend sglang-oai-chat \
  --dataset-name oracle-trace \
  --dataset-path ./combined.json \
  --model <served-model-name> \
  --num-prompts 50 \
  --max-concurrency 8
```

Or just `TOKENIZER=... MODEL=... PAYLOADS_GLOB=... ./run_bench.sh` to do both
steps. Different rollouts run concurrently (up to `--max-concurrency`); turns
*within* one rollout still run sequentially, same ordering guarantee as
`replay.py` -- `wrap_multi_turn_request_func` (in `sglang/benchmark/serving.py`)
handles that, and now also strips reasoning from history between rounds
(`_strip_reasoning_for_history`) for the same realism reason as `build_trace.py`'s
`strip_reasoning`.

`--combined-output`'s format differs from `--output-dir`'s: each turn holds
only the messages *new* since the previous turn (a delta), since
`wrap_multi_turn_request_func` fills in the assistant slot itself from the
server's own (forced) reply. See `oracle_trace.py`'s docstring for the exact
shape.

#### 3c. Sustained per-GPU scorecard

The **concurrent_replay.py** entry point is the maintained driver for long,
saturated throughput runs. It preserves turn ordering within each
conversation, reports true counter deltas for a fixed post-warmup window, and
writes enough provenance to audit the denominator later.

The metric is:

~~~text
served TPM/GPU = (prompt tokens + completion tokens) / elapsed seconds
                 * 60 / physical GPUs
~~~

The physical GPU count, GPU model, topology, and output path are required.
When CUDA_VISIBLE_DEVICES is set for a single-node run, its device count must
match the physical GPU count; this catches the old failure mode where a TP2 run
was silently divided by four. Multi-node runs must opt in and still record the
full topology.

Example four-GPU score run:

~~~bash
CUDA_VISIBLE_DEVICES=0,1,2,3 python3 concurrent_replay.py \
  --base-url http://127.0.0.1:30002 \
  --server-info-url http://127.0.0.1:30002 \
  --model m3 \
  --dataset /path/to/oracle-prod-800.json \
  --n-convs 800 \
  --concurrency 256 \
  --max-in-flight 48 \
  --max-turns 25 \
  --warmup-seconds 60 \
  --measurement-seconds 600 \
  --stream \
  --physical-gpus 4 \
  --gpu-model "NVIDIA B200" \
  --topology "1 node; TP4+EP4; GPUs 0,1,2,3" \
  --min-fixed-tpm-per-gpu 3000000 \
  --min-drain-tpm-per-gpu 2850000 \
  --out results/m3-b200-tp4-run1.json
~~~

The default scorecard fails closed unless the fixed window has zero request
failures, 94-96% actual prompt-cache hits, and a 0.65-0.85% output-token share.
It also records the separate interactive target of TTFT p50 at or below 3
seconds. Use **--allow-scorecard-failure** only for explicit calibration runs;
the JSON retains the failed gates. If traffic naturally ends before the
requested window, the fixed result is invalid rather than silently shortened.

Use **--concurrency** for the number of live conversation workers and
**--max-in-flight** for the admission cap. This reproduces a 256-client,
48-active-request workload without relying on a gateway limiter. Admission is
strict FIFO, and its wait is included in user-observed TTFT rather than hidden.

For a router with multiple replicas, repeat **--server-info-url** for the
direct worker endpoints as well as routing traffic through **--base-url**.
This records the actual server launch configuration rather than only the
router's worker count.

To bypass a router and keep every conversation on one replica, repeat
**--worker-base-url** instead. The driver assigns conversation index modulo
worker count, which is deterministic, balanced, and sticky across turns. Do
not combine **--worker-base-url** with **--base-url**.

#### Scope

Oracle mode only forces plain (non-speculative) decode/prefill today. If the
server is running DFlash speculative decoding, forced tokens won't take
effect there -- see `feat/oracle-decode-mode`'s commit message.
