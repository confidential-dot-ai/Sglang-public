# DeepSeek-V4.1 on 8x B300 at 1M context: topology and memory plan

Unqualified. Everything here is derived from the B200 CC VM; nothing has booted
on a B300. `container/dsv41-b300-1m.env` is the starting recipe.

## Launcher: N prefill + M decode workers

`launch.py` takes `--num-prefill N --num-decode M --prefill-tp T --decode-tp U`
(TP = EP, sizes 2/4/8; TP1 cannot hold the ~294 GiB of weights). GPUs are
assigned in worker order, prefill first (`--gpus` lists N*T + M*U indices).
Ports: router `--port`; prefill i `port+1+i`, bootstrap `bootstrap-port+i`, NCCL
`nccl-port+i`; decode j `port+1+N+j`, NCCL `nccl-port+N+j`. Every 1P1D and
N-prefill/1-decode plan is byte-identical to before.

The router gets one `--prefill URL BOOTSTRAP` per prefill and one `--decode URL`
per decode. With more than one worker in a role, that role uses the `manual`
policy with `--assignment-mode min_group`: each `X-SMG-Routing-Key` (the replay
driver sends `conv-<i>`) sticks to one prefill and one decode, with a separate
sticky map per role. Prefill stickiness keeps a conversation's radix + HiCache
prefix on one worker; decode stickiness is what a decode radix cache needs.
Unkeyed requests are routed randomly, so production clients must send the key.

Dry-run plans (8 GPUs, B300 profile, 1M context):

| Plan | Workers | Router policy |
| --- | --- | --- |
| 3P1D | prefill0-2 GPUs 0-5, decode 6-7 | prefill manual |
| 1P3D | prefill 0-1, decode0-2 GPUs 2-7 | decode manual |
| 2P2D | prefill0-1 GPUs 0-3, decode0-1 GPUs 4-7 | both manual |
| 1P(TP4)+2D | prefill GPUs 0-3, decode0-1 GPUs 4-7 | decode manual |
| 2P+1D(TP4) | prefill0-1 GPUs 0-3, decode GPUs 4-7 | prefill manual |

## Memory model (`--memory-profile`)

Per-rank costs measured from the release-21eacbd216 TP2 pair (2026-10-19):

| Item | Value |
| --- | --- |
| HBM (B200 memory.total) | 179.06 GiB; B300 288 GB nominal = 268.2 GiB |
| CC context + runtime before weights | 3.81 GiB |
| Weights, target + DSpark draft, TP2 | 146.76 GiB (TP4/TP8 estimated as even sharding + 5%) |
| KV per token, target + draft | 1938 B |
| Sliding-window ring per request or prefix tail | 10.5 MiB |
| Prefill graphs, chunk 12288 / 16384 | 12.68 / 15.28 GiB; decode graphs 1.75 GiB |

`pool = min(HBM - context - weights - graphs - transient reserve,
HBM * mem-fraction - weights) - rings`, rounded down to 64K tokens.
`--max-total-tokens auto` / `--decode-max-total-tokens auto` use it; the plan
records the estimate under `memory`. On B200 it reproduces today's pair: 10.2
GiB predicted vs 9.67 GiB measured free on prefill, 18.5 vs 18.1 on decode.

The transient reserve (`--prefill-transient-reserve-gib 10`,
`--decode-transient-reserve-gib 6`) is a placeholder for real accounting of the
eager indexer's logits tiles and other transients, which grow with context: at
chunk 16384 prefill ran out of memory with ~7 GiB free. Replace the defaults
when that accounting exists; 1M-context prefill may need more.

| Per rank, B300, 1M context, mem-fraction 0.92 | Prefill TP2 | Prefill TP4 | Decode TP2 | Decode TP4 |
| --- | ---: | ---: | ---: | ---: |
| KV pool | 51.1M tokens | 89.7M | 55.0M | 93.7M |
| 1M-token contexts resident | 48 | 85 | 52 | 89 |
| HBM left free | 10.0 GiB | 10.1 GiB | 16.0 GiB | 15.9 GiB |

A 1M-token context is ~1.8 GiB of KV per rank, so HBM is not what limits 1M
serving on B300; prefill compute (~50 s per cold 1M prompt on one TP2 prefill)
and host RAM are.

## Host RAM

HiCache is sized per rank with `--prefill-hicache-size-gib` (`--hicache-size`).
A ratio would not fit: 4x a 51M-token pool is ~740 GiB per prefill worker.
Preflight now adds every prefill worker's host pools to the Engram and reserve
requirement. The recipe's 64 GiB x 2 ranks x 3 prefill workers = 384 GiB, plus
the ~189 GiB Engram holder and the 32 GiB reserve, needs ~605 GiB available.
Without `--cpu-engram-staging`, every TP group allocates its own Engram table,
so preflight counts N+M tables.

## Not yet validated

- No B300 boot: HBM total, weights per rank at TP4/TP8, graph and transient
  sizes are estimates until preflight and the first boot confirm them.
- Workers start one at a time (~5 min of weight loading each); `--parallel-load`
  overlaps them.
- The bench profile's `oracle-proxy` addresses one prefill/decode pair only.
- 1M context itself (graphs past 64K, indexer memory, position indexing, KV
  transfer) is covered by separate work.
