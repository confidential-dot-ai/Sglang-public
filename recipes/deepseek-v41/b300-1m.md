# DeepSeek-V4.1 on 8x B300 at 1M context: topology and memory plan

Unqualified. Everything here is derived from the B200 CC VM; nothing has booted
on a B300, and the CED-split PP2 prefill (`ced-pp2.sh`) was GPU-validated only
on the pp-encoder branch, before the upstream merge. `container/dsv41-b300-1m.env`
is the starting recipe.

## Layout

| Worker | GPUs | Parallelism | Runs |
| --- | --- | --- | --- |
| prefill0, prefill1 | 0-1, 2-3 | PP2, TP1 per stage, stages 0-7 / 8-20 | CED split: encoder layers 0-20 only, no DSpark |
| decode0, decode1 | 4-5, 6-7 | TP2/EP2 | DSpark; replays each prompt's tail through every layer |

Both roles route by `X-SMG-Routing-Key` (`manual`, `--assignment-mode
min_group`, one sticky map per role): a conversation keeps its prefill radix +
HiCache prefix on one prefill and its decode on one decode. Unkeyed requests are
routed randomly, so clients must send the key; the replay driver sends
`conv-<i>`. Cold 1M-token prompts are not the optimization target.

The stage split must sit at a kv_source layer (2, 8, 14, 20): layers 8-13 read
layer 8's compressed KV and top-k. 8/13 is the most even split available (14/7
puts 14 layers on one stage); it leaves stage 1 with 13 of 21 layers, so the
pipeline is bounded by stage 1.

## Launcher

`launch.py` takes `--num-prefill N --num-decode M --prefill-tp T --decode-tp U`
(TP = EP, 2/4/8). With `--prefill-pp 2` a prefill worker is two GPUs at TP1 per
stage. GPUs are assigned in worker order, prefill first. Ports: router `--port`;
prefill i `port+1+i`, bootstrap `bootstrap-port+i`, NCCL `nccl-port+i`; decode j
`port+1+N+j`, NCCL `nccl-port+N+j`. Every existing plan is unchanged apart from
the topology label of PP plans, which now reads `PP2xTP1` instead of `TP2`.

Dry-run plans (scratch `topo/plans/`): `b300-1m-env.json` is the recipe;
`nondefault-*` keep the TP2/TP4 N:M layouts (3P1D, 1P3D, 2P2D, TP4 prefill +
2 decodes, 2 prefills + TP4 decode) as non-default options.

## How the current flags compose with CED PP2

| Flag | On a CED PP2 prefill | Notes |
| --- | --- | --- |
| `SGLANG_ENABLE_DISAGG_PREFILL_EARLY_RESULT` | no effect | Read only in the overlap loop; `--pp-size > 1` turns overlap off and runs `event_loop_pp_disagg_prefill`. Dropped from the recipe. |
| `SGLANG_HRRN_SIZE_EXPONENT` / HRRN | applies | The PP loop forms batches through `get_new_batch_prefill`. |
| `SGLANG_OPT_PREFIX_PROMPT_ENCODE` | applies, both roles | Tokenizer-side; independent of PP/CED. |
| Prefill HiCache | wired, unvalidated | The PP loop processes HiCache events, and storage shards by PP rank; no run of HiCache + PP2 + CED on record. |
| Engram staging | applies per stage | Engram layers 1 and 14 fall on stages 0 and 1; each stage stages only its own table. |
| Custom all-reduce | prefill skipped | A TP1 stage has no TP group; preflight probes only decode. |
| Decode radix cache (agent A) | risk | The CED tail path (`disaggregation/decode.py` ~3367-3374) calls `init_next_round_input(tree_cache)`, where a decode radix match would set the prefix, then overwrites `prefix_len` with `tail_start`. With the radix cache on, the matched (and locked) prefix and the replayed prefix would disagree. Untested; not implemented here. |
| 1M context | bounded tails | The CED tail is at most one SWA window plus a page (~384 tokens) at any length. The replay's late layers score layer 20's candidates over every compressed position, so the decode transient (indexer tiles, up to 2 GiB each) grows with context. CED decode graph memory is unmeasured. |

The launcher enforces `--prefill-pp 2` with `--prefill-tp 2`, CED on both roles
(`SGLANG_OPT_DSV41_CED_SPLIT=1`), `SGLANG_PP_LAYER_PARTITION=8,13`, and no
speculative flags on prefill. The PD transfer allows prefill TP1 to decode TP2
for CED (`common/conn.py`).

## Memory model (`--memory-profile`)

Per-rank costs, measured from the release-21eacbd216 TP2 pair (2026-10-19)
unless marked:

| Item | Value |
| --- | --- |
| HBM (B200 memory.total) | 179.06 GiB; B300 288 GB nominal = 268.2 GiB (estimated) |
| CC context + runtime before weights | 3.81 GiB |
| Weights, TP2 rank, target + DSpark draft | 146.76 GiB (= 0.998x half the checkpoint) |
| Weights, CED stage 0-7 / 8-20, TP1, all experts | 57.33 / 90.69 GiB (from checkpoint tensor bytes; estimated) |
| KV per token, all 40 layers + draft | 1938 B (derived 1902 B + draft) |
| KV per token, CED stage 0-7 / 8-20 | 326 / 1304 B (derived from owner layers; estimated) |
| Sliding-window ring per request or prefix tail | 10.5 MiB for 40 layers; stages take 8/40 and 13/40 (estimated) |
| Prefill graphs, chunk 12288 | 12.68 GiB, assumed per stage (estimated); decode graphs 1.75 GiB |

`pool = min(HBM - context - weights - graphs - transient reserve,
HBM * mem-fraction - weights) - rings`, rounded down to 64K tokens; a PP prefill
takes the smaller of its two stages. `--max-total-tokens auto` and
`--decode-max-total-tokens auto` use it, and the plan records it under `memory`.
On B200 it reproduces today's TP2 pair: 10.2 GiB predicted vs 9.67 GiB measured
free on prefill, 18.5 vs 18.1 on decode. The transient reserves
(`--prefill-transient-reserve-gib 10`, `--decode-transient-reserve-gib 6`) are
placeholders for real transient accounting.

| Per rank, 1M context, mem-fraction 0.92 | B300 | B200 |
| --- | ---: | ---: |
| CED prefill pool, shared by both stages | 123.6M tokens (117 x 1M) | 50.2M (47 x 1M) |
| Stage 0-7: weights / pool / free | 57.3 / 38.1 / 156.3 GiB | 57.3 / 15.8 / 89.4 GiB |
| Stage 8-20: weights / pool / free | 90.7 / 151.0 / 10.0 GiB | 90.7 / 61.9 / 10.0 GiB |
| TP2 CED decode pool | 55.0M tokens (52 x 1M), 16.0 GiB free | 9.6M (9 x 1M), 8.8 GiB free |

On B300 the decode pool is capped by `--mem-fraction`, so a larger decode
transient reserve (up to ~16 GiB) costs no pool. Stage 0 carries ~156 GiB it
cannot use: the pool is shared, and stage 1 sets it.

## Host RAM

HiCache is sized per stage rank with `--prefill-hicache-size-gib`
(`--hicache-size`): 32 GiB x 2 stages x 2 workers = 128 GiB. With ~117 1M-token
contexts resident on each prefill's GPUs, the host tier is a small overflow.
Preflight adds every prefill worker's host pools to the Engram (~189 GiB holder)
and the 32 GiB reserve.

## Router and oracle proxy for 2P2D

- Router: one `--prefill URL BOOTSTRAP` per prefill and one `--decode URL` per
  decode, `--prefill-policy manual --decode-policy manual --assignment-mode
  min_group`; `launch.py` emits this. The shipped router and in-tree source
  both key `manual` on `X-SMG-Routing-Key` per role.
- `oracle_pd_proxy.py` already routes across several prefills (repeat
  `--prefill-url URL@BOOTSTRAP`, sticky by key) but takes one `--decode-url`.
  2P2D oracle runs need a repeatable `--decode-url` with the same sticky
  selection, and compose's `oracle-proxy` service must pass both prefills and
  both decodes; today it passes one of each.
